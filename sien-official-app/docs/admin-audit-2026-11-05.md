## 結論

今は機能を大きく増やすより、**「保存結果がわかる」「同じ内容を何度も入力しない」「間違えても戻せる」管理画面**にするのがおすすめ。

依頼管理・金額管理の統合方針は維持してよい。プロフィール、サービス説明、料金、FAQは用途が異なり、単純な重複ではない。お知らせとブログは画面を分けたまま、裏側の編集部品を共通化すると保守しやすい。

確認できた不具合は修正した。追加機能、大きな構成変更、未使用コードの削除は以下の提案に分け、今回は実行していない。

## 修正した不具合・不備

| 対象 | 問題 | 修正 |
|---|---|---|
| 経費・売上目標 | `parseInt` により小数・余分な文字付きの金額を一部だけ保存できる | 0円以上の整数を厳密検証。不正な金額・日付・空欄は保存しない |
| 経費操作 | HTTPエラーでも何も表示せず、保存できたか判断しづらい | エラー内容を表示し、編集中の値を保持。処理中の重複操作を抑止 |
| 経費の日付 | 日本時間の0時をUTCに直して日付欄に戻すと前日になる | 登録・表示・編集で日本時間の日付を使用 |
| プロフィールとサイト共通情報 | 1つの保存操作なのに2回の書き込み。後半だけ失敗すると部分保存 | 両方を先に検証し、1つのDBトランザクションで保存 |
| 受付設定 | 不正な受付状態や未指定値が「受付中」扱いになる余地 | 許可された3状態だけを受け付ける。未知の値で受付再開しない |
| 掲載内容の入力 | URL、評価、記事種別、空白だけの文章などを保存できる箇所 | サーバー側でも検証。項目を限定して保存し、不正なリンク等を拒否 |
| レビュー並べ替え | 並列の個別更新で途中だけ保存。HTTPエラーを成功扱いし画面だけ並べ替える | 1回のAPI・1つのトランザクションへ変更。古い一覧は競合として拒否。成功後だけ表示を更新 |
| 実績の並べ替え・一括操作 | 並び順の途中保存、自動保存の古い値が一括変更を後から上書きする余地 | 並べ替えをトランザクション化。一括変更・削除前に保留中の保存を完了させる |
| 新規実績 | 追加ボタンだけで「新規実績」という未完成データを公開扱いで作成 | 新規プレースホルダーは非公開で作成 |
| 記事の保存・削除 | 保存中の再操作ができ、削除は1クリックで実行 | 処理中のボタンを無効化。削除は画面内の二段階確認に変更 |
| 記事編集URL | ブログ編集URLからお知らせIDを開くと種類を変更する余地 | 編集画面で記事種別も照合し、別種別は開かない |
| CSV | カテゴリやタイトルのカンマ・引用符で列が崩れる。数式形式の文字列をそのまま出力 | 文字列のクォートを共通化し、数式形式を無効化。売上行に依頼者名と案件IDを表示 |
| キャンペーン表示 | 有効フラグだけで「開催中」を判断し、期限切れも開催中になる | 開始前・開催中・終了・停止中・対象未設定を区別 |
| キャンペーン対象 | 空欄を「全対象」と説明するが、実際には対象プランID一致のものしか割引しない | 誤った説明を修正。既存プランから選択し、存在しない対象を登録しない |
| 設定画面の導線 | プロフィール・FAQ・サービス説明等の画面が存在しても通常のメニューから到達しづらい | 設定画面に既存4画面への入口を追加 |
| 依頼一覧 | 「すべて」で見ていても並び順・絞り込み操作で進行中表示に戻る | 選択中の表示状態をURLに保持 |
| 依頼詳細 | 金額欄の保存で別の依頼編集欄が再作成され、未保存入力を失う余地 | 案件IDを単位に編集欄を維持 |
| 読み込み失敗 | 管理画面の読み込みエラー時に戻り先や保存確認の案内がない | 管理画面用の再読み込み・ダッシュボードへの案内を追加 |
| 文言・操作名 | お知らせに「ブログ用」の表記、実装されていないAI生成の予告、名前のない操作欄 | 誤記・予告を整理し、主要な入力・操作にラベルを付与 |

実績の既存データや公開区分、法人問い合わせを一括で変更していない。記事の削除は、確認後に確定すると従来どおり完全削除であり、ごみ箱はまだない。

## 重複・未使用の整理候補

| 候補 | 確認結果とおすすめ |
|---|---|
| `DeadlinePanel` / `FinancePanel` / `OrderActions` | 現行ソースで画面からの参照がなく、依頼詳細の新しい編集欄と役割が重なる。利用確認後にコードを整理する候補。今回は削除していない |
| `BusinessListClient` | 統合後の法人一覧は依頼管理を使い、旧一覧部品は現行画面から参照されていない。削除候補だが `BusinessContact` の元データや旧URLは残す |
| 旧法人更新API 2系統 | 統合後の更新導線と重なる。旧通知URL・互換利用の確認後に整理する。データ保持のため旧法人詳細からの移行導線は残す |
| `updateProfile` / `updateSiteSettings` 個別処理 | 現行画面はまとめて保存する処理へ変更。個別の書き込み処理は参照先を確認したうえで整理できる |
| お知らせ・ブログの編集コード | 画面の用途は別だが実装が重複。共通エディタ化すると不具合修正を片方へ反映し忘れにくくなる。管理項目自体は分けてよい |
| FAQ・サービス・キャンペーンの更新処理 | 更新のコードはあるが画面から使われていない。不要と決めて削除するより、上記の編集UIに活用するのがおすすめ |
| `/api/posts` | 現行画面は主にServer Actionsを使い、ソース内でこのAPIの利用箇所は見つからない。外部利用の有無までは断定できないため削除していない。未対応の `WORKS` を既定で作る挙動は修正した |

「コードから参照がない」ことと「ユーザーが使っていない」ことは区別した。アクセス履歴や外部ツール利用を確認せずに既存API・保存データを削除していない。

## 検証と本番への影響

- 既存・追加テスト、型検査、Lint、隔離DBを使う本番形式のビルドを実施。
- `qa-admin-audit.mjs` で主要22画面、経費・目標額、レビューの保存、競合、後続行失敗時のロールバックを検証。
- ブラウザーで不正URL時にプロフィールだけが保存されないこと、不正金額の保持・拒否、日付、レビュー並べ替えの再読み込み後の保持、CSV出力を確認。
- プレビューの変更は架空データのみ。外部メール・Discordの実送信、本番データの移行、公開は実施していない。
- 秋のMIXセールの保留状態を継続。固定価格キャンペーンの操作で秋セールの公開スイッチを変更することはない。

今回の追加点検・修正自体には新しいDBカラムは不要。ただし前回の依頼統合で追加したスキーマと移行は引き続き必要で、導入手順は `admin-integration-preview.md` を参照する。
